# Фоновые задачи Codex

Codex можно выбрать для задачи с `type: event`, `runtime: drain`, `workspace: worktree`. Каждая задача работает через отдельный App Server на той же Linux-машине и наследует текущие модель, effort и аккаунт Codex. Шаблон Claude остаётся отдельным; без выбора движка новые задачи используют Claude.

```bash
claude-rc agent new-task --engine codex --name task-example --project example --text 'Внеси согласованную правку'
```

Из Telegram: `/new --engine codex example Внеси согласованную правку`. Последующие сообщения передаются обычной командой `/task task-example …`.

Установщик создаёт отсутствующий `~/.claude-control/task-codex-template.yaml`. Свой шаблон можно выбрать через `CLAUDE_RC_CODEX_TASK_TEMPLATE`; существующий файл установщик не перезаписывает. Для Codex не поддерживаются mission, direct/shared workspace и handoff. Стоимость в долларах неизвестна: денежный лимит запрещает запуск вместо предположения о бесплатной работе.

## Требования

Поддерживается закреплённый native Codex CLI 0.160.0 для Linux x86_64 с соответствующими `codex-code-mode-host`, `bwrap` и `rg`. Нужны user systemd, рабочий вход в Codex и установленное Python-окружение `websockets==15.0.1`. Бинарные файлы и все их каталоги должны принадлежать root или текущему пользователю и не разрешать запись группе/остальным. Каталоги native истории в `CODEX_HOME/sessions` также не должны разрешать такую запись; сами файлы истории имеют режим0600. Обычная npm-установка может иметь режим0775: проверь права при отказе допуска; смена версии или произвольная замена бинарных файлов не является ремонтом задачи.

```bash
codex-task-runtime preflight "$HOME/.claude-control/agents/task-example"
```

Preflight проверяет статические условия; свободную память и запуск процесса проверяет исполнитель. На первый запуск требуется дополнительный служебный ход модели для проверки доступных инструментов. Изменение конфигурации, инструментов или сохранённого диалога может остановить дальнейшую работу.

## Вопросы и завершение

Модель может читать и менять файлы своего worktree, пользоваться `task_read`, `task_search`, `task_list`, `task_ask` и `task_done`. Shell, Git, сеть и дополнительные MCP-инструменты ей недоступны. Доверенный исполнитель делает checkpoint после остановки всех процессов задачи.

Обычный вопрос задачи приостанавливает очередь. Ответ через карточку Telegram или `claude-agent-answer` продолжает работу отдельным ходом. Запрос native file approval адресуется текущему действию: разрешение допустимо только внутри исходной области доступа. Для полного запроса на изменение снаружи карточка позволяет только отказать. Ответ на такой запрос не создаёт дополнительный ход модели.

`task_done` создаёт запрос приёмки после остановки процесса и сохранения checkpoint. Результат остаётся на обычной человеческой проверке; кнопки приёмки, отклонения и отмены используют общую TASK-процедуру.

## Остановка и восстановление

Пауза и отмена идут через обычные `claude-rc agent pause` и `claude-rc agent task-cancel`. Не удаляй приватный реестр `~/.claude-control/codex-task-state`: он доказывает, какие процессы принадлежат задаче и были ли они остановлены. Потеря записи или неоднозначный ответ native-сервера останавливает выполнение и сохраняет данные для разбора; новый пустой реестр не восстанавливает это доказательство.

`codex-task-runtime reconcile <agent-directory>` восстанавливает подтверждённые этапы завершения под executor lock. Занятый lock означает, что исполнитель ещё владеет задачей. Проверка остановки доступна через `codex-task-runtime barrier <agent-directory> --reason recovery`; успешный ответ подтверждает остановку всех известных процессов этой задачи. Прямой `execute` предназначен для доверенного runner и требует действующего lease и события в inflight.
