## Закрытый контракт ядра журнала для отдельного DESIGN/RED

Ядро не подключается к сети и не запускает процессы. Транспорт и HTTP проверяются отдельными слоями. Класс `NodeTaskStore(path, clock=...)` создаёт приватный SQLite-файл вне репозитория; родительский каталог принадлежит текущему пользователю, без ссылок, mode0700; файл0600. Открытие существующего файла с неверными правами/типом/версией схемы отказывает. Не следовать symlink и не создавать БД поверх чужого файла. Один process owner, собственный threading lock; WAL/FULL и транзакции. Ledger — единственная очередь, второй outbox не создаётся.

Публичные методы ядра:
- `submit(request_id, node_id, prompt)` принимает canonical UUID, только `alp`, UTF-8 строку1..32768B без NUL. Повтор того же ID и точных полей возвращает ту же задачу; иной payload — `conflict`. Сервер выбирает task_id=request_id и единственный command message_id при первом commit. Envelope exact v1, source=`control-web`, target=`codex-ai-dev-1`, kind=`submit`, correlation_id=task_id. `created_at` фиксируется в UTC один раз. В outbox сохраняются исходные bytes. Общий незавершённый backlog<=32; известный повтор не расходует новую квоту.
- `pending(limit=1)` возвращает только сохранённые идентификаторы и bytes, не меняя задачу. Учитывает backoff. `publication(task_id, message_id, sequence)` идемпотентно фиксирует подтверждение DEVBUS_V1; неподтверждённое время ожидания остаётся отдельным delivery=`unknown`. `publish_failed(task_id)` увеличивает backoff c максимумом60s, не меняет bytes/ID и не объявляет execution failed. Worker не должен повторять task с terminal execution или после объявленного разрыва retention.
- `ingest(event)` принимает только exact schema v1 и ограничение wire<=126KiB (запас под NATS headers), затем проверяет source=`codex-ai-dev-1`, target=`control-web`, task/correlation. Типы событий: accepted, running, completed, failed, needs_attention. Для completed payload только text:str/executor=`codex`/optional output_truncated:bool; bounded JSON<=60000B. Для failed — известная причина и nullable integer exit_code, без raw exception. Неподдержанные payload не превращаются в результат. Raw внешние строки не исполняются и не вставляются в HTML. Дубликат event_id+digest не меняет состояние; конфликт event_id помечает задачу needs_attention и сохраняет факт конфликта. Незнакомые task_id не создают задачи.
- `get(task_id)` и `list(limit=50)` возвращают bounded owner DTO, без NATS credentials, локальных путей, команд CLI и чужих задач. `close()` закрывает соединение.

DTO: `schema=1`, `task_id`, `node_id`, `prompt`, `created_at`, `updated_at`, `delivery` (`pending`, `published`, `unknown`), `execution` (`waiting`, `accepted`, `running`, `completed`, `failed`, `needs_attention`), `result` (null либо bounded text/executor/output_truncated), `quality`=`unreviewed`, `usage`=null, `coverage` (`complete`, `partial`). Поле published не заменяет accepted; пришедшее событие может подтвердить исполнение даже при потерянном PubAck. Переход running→accepted при replay не откатывает состояние. После completed/failed поздний accepted/running не откатывает terminal. Разные terminal outcomes требуют внимания и partial coverage. Само отсутствие событий не доказывает сбой исполнения.

Закрытое ядро не обещает structured usage: текущий runner его не публикует. UI обязан показать «Расход неизвестен»; расширение native usage — отдельный child, а не вычисление из ответа LLM. Родитель CONTROL-EXECUTION-NODES не закрывается этим ядром.

Приёмка ядра: reopen после commit сохраняет bytes/ID/result; competing submit одногоID не создаёт вторую task; conflict/malformed/oversize/disk-error fail closed; повтор/reorder событий не удваивает результат; restart и истёкший backoff не создают новый ID; неизвестные поля/чужие source/target/task отвергаются. Тесты не требуют NATS, SSH, vendor auth или inference.

## Уточнения ядра после DESIGN

1. Worker один, дополнительного lease/in-flight состояния нет. `publication_started(task_id)` атомарно ставит delivery=unknown до сетевого вызова. Pending/unknown с наступившим retry_at снова выдаются после рестарта с теми же bytes/ID. Только успешный PubAck переводит в published; crash после публикации, но до записи ACK, приводит к повтору исходной команды, которую долговечно дедуплицирует runner. Это не exactly-once процесса.
2. `publication(task_id,message_id,wire_sha256,sequence)` сверяет ID и SHA с сохранённым outbox; sequence — положительный int. Повтор ACK с другой sequence допустим: после broker duplicate window повторные bytes могут получить новую stream sequence, но runner узнаёт прежний task_id. Сохраняются первая/последняя sequence, задача не создаётся заново. Несовпадение ID/SHA — conflict. Не требовать равенства stream sequence между транспортными повторениями.
3. `ingest(raw:bytes)` считает SHA256 над точными принятыми wire bytes после strict JSON decode (UTF-8, duplicate keys/nonfinite отвергаются). Изменение кодирования при том же message_id считается конфликтом, потому что publisher обязан сохранять immutable bytes. На диск идут event_id/digest/kind/time и транзакционная проекция; произвольный raw payload не дублируется в event table. Итоговый bounded result хранится в строке задачи.
4. Незнакомая task или чужой source/target/correlation возвращает `ignored`, увеличивает bounded diagnostic counter, не создаёт task и не меняет чужую задачу. Malformed wire возвращает `invalid`; consumer может ACK после фиксации bounded counter, чтобы одно чужое событие не удерживало очередь. Ответы ядра не содержат raw payload/errors. Конфликт уже известного event_id фиксируется как needs_attention для связанной задачи.
5. Порядок нетерминальных состояний: waiting < accepted < running. События accepted/running берут максимум этого порядка. completed/failed из любого нетерминального состояния задаёт terminal. После terminal accepted/running игнорируются. Повтор terminal того же вида с тем же canonical payload digest не меняет результат, даже при новом event_id; другой вид или другой payload digest переводит в needs_attention и сохраняет первый результат как исторический. needs_attention не снимается следующими событиями автоматически. Любой explicit needs_attention также требует внимания.
6. coverage изначально complete означает только «нет обнаруженного разрыва для этой задачи», не полноту всей шины. `mark_gap()` делает coverage=partial для незавершённых задач и запрещает автоматическую повторную публикацию затронутых записей; сообщения о конфликтах также делают partial. Partial не возвращается в complete автоматически. UI объясняет границу покрытия.
7. Пределы: 1000 сохранённых задач, 32 незавершённых, 256 event digest rows на задачу, SQLite main DB256MiB через max_page_count, WAL с регулярным checkpoint и без долгих read transactions. Нет автоматического удаления. Submit сверх лимита → capacity error до публикации. Event limit → retained needs_attention/partial и bounded diagnostic counter, без сохранения дополнительных payload. При disk-full/commit failure не выдавать success и не ACK событие; producer сможет повторить после восстановления места.
8. Submit возвращает DTO/task_id только после успешного commit. Неопределённый результат commit возвращает generic storage error без утверждения, что task создана или не создана. Повтор с тем же request_id восстанавливает результат; новый ID автоматически не выдаётся.
9. Хранилище — приватный каталог доверенного service UID; другой UID не может менять имена файлов. Проверки каталога/существующих leaf выполняются через directory fd и O_NOFOLLOW+fstat; существующие symlink/hardlink/чужие владельцы отвергаются до SQLite. SQLite stdlib не предоставляет SQLITE_OPEN_NOFOLLOW как connect flag, поэтому не заявляется защита от злонамеренного процесса с тем же UID (он уже может менять код/credentials этого сервиса). Единственный writer и приватный каталог — граница эксплуатации; сверить inode/mode до и после connect, резервировать новый файл O_EXCL и сохранять FD на время открытия. Не добавлять ctypes/новую зависимость ради ложного обещания same-UID isolation.

### Python seam для независимых тестов ядра
Модуль bin/_control_node_tasks.py, класс NodeTaskStore. Public методы возвращают dict/list; ошибки операций — ровно {'error': code} с code из invalid_request/conflict/capacity/storage/not_found. Constructor на unsafe path/schema или невозможности открытия бросает ValueError без raw path/exception. pending(limit) возвращает list элементов с полями task_id/message_id/wire(bytes)/wire_sha256; только execution=waiting, coverage=complete и наступивший retry_at. publication_started(task_id) возвращает {'publish': True} после commit unknown, либо {'publish': False} если задача уже не ожидает публикации; worker не отправляет при False. publication и publish_failed возвращают актуальный task DTO. ingest возвращает {'outcome': applied|duplicate|ignored|invalid|conflict, 'task_id': UUID|null} либо storage error. mark_gap() возвращает {'affected': nonnegative_int}. list упорядочен по created_at/task_id, limit1..50; get неизвестного ID — not_found. Счётчики диагностики насыщаются на2147483647. Read methods не возвращают внутренних путей или секретов.

### Exact v1 и существующие payload
Envelope имеет ровно message_id/task_id/correlation_id/source/target/kind/created_at/payload, без добавочного schema. Строковые wire IDs соответствуют [A-Za-z0-9_-]{1,80}; task/requestID Control дополнительно canonicalUUID. created_at — timezone-aware ISO8601; producer Control пишет UTC. accepted/running payload ровно {}. failed reason из timeout/output_limit/executor_exit/local_executor_error; exit_code optional int|null (local_executor_error его не содержит). needs_attention payload ровно {'reason': 'interrupted; outcome unknown; automatic retry disabled'}. completed — text/executor и optional output_truncated. Не принимать произвольную причину как raw exception.

### Уточнения после SOURCE ядра
Отсутствие lease преднамеренно: немедленный повтор после crash безопасен только с durable dedup runner, что требуется до live включения. Переход publication_started→unknown не обязан ждать backoff до первого восстановления. Время external created_at сохраняется как provenance, не используется для порядка состояний или UI updated_at (используется clock Control).

При event cap новый digest не принимается и не сохраняется: это capacity refusal с partial/needs_attention, а не обещание дедупликации неограниченного набора отклонённых событий. После первого перевода в needs_attention повторные capacity refusals не двигают updated_at; bounded diagnostic counter может считать отказы. Если attention возник до первого результата, поздний валидный completed сохраняет первый результат для проверки, но не снимает needs_attention/partial.

Existing schema v1 должна совпадать по ограничениям PK/UNIQUE, внешнему ключу и обязательному индексу, а не только названиям столбцов. Все пройденные ancestors принадлежат root или service UID и не доступны на запись группе/остальным; исключение только root-owned sticky /tmp и /var/tmp. Same-UID adversary по-прежнему вне обещаний.


### Служебные события общего subject
Валидные exact-v1 heartbeat/registration с payload:dict не являются исходами задач. После strict envelope/UTF8/duplicate-key/nonfinite/ID/time/wire-limit проверки ядро возвращает ignored/task_id=null и коммитит bounded diagnostic counter до ACK, до любого task lookup или event-ID dispatch. Содержимое metadata dict не интерпретируется как authority; даже совпадающий owned task_id не изменяет task/result/fence. Metadata не заполняют task event digest table. Malformed envelope или payload не dict остаются invalid. Result payload limit60000B относится к исходам задач, metadata ограничены общим wire126KiB.


### Повреждение сохранённых данных
При открытии schema2 проверить ровно одну metadata singleton=1 row; fence допустим только null/retention_gap/invalid_event/id_conflict. Отсутствующая row, BLOB или неизвестное значение означают generic ValueError до изменения schema/data/journal settings; не восстанавливать singleton автоматически. Ошибка декодирования сохранённого result в операции означает generic storage error и немедленный rollback: следующая независимая исправная операция проходит без дополнительного «лечащего» вызова. Повреждённое значение не удаляется и не переписывается автоматически.
