# Android: форма входа при возврате из KeePass

Владелец: `CONTROL-APP-LOGIN-LIFECYCLE` (parent `CONTROL-APP-AUTH-RELEASE`).
Исходная принятая версия: `082afbdc83d02e213522a579aeff1bfa82daca0f`, APK 0.1.2/code 3.
Решение пользователя: 07.10.2026. Этот ограниченный addendum дополняет
[Android](../specs/android-client.md) и [app-auth](../specs/app-auth.md).

## Проблема и требуемое поведение

До первого входа пользователь заполняет логин, переключается в KeePass,
копирует пароль, возвращается и вставляет его. Затем снова переключается
в KeePass за TOTP, возвращается и вставляет код. Сейчас возврат пересоздаёт
форму, поэтому предыдущие поля исчезают и вход невозможно завершить.

Обычный `onStop()` → `onStart()` той же живой `MainActivity` сохраняет уже
видимую форму и её поля в памяти этой Activity. Значения логина, пароля и
TOTP остаются точными, включая пробелы и регистр. Текущее поле фокуса и
выделение сохраняются, когда Android позволяет сохранить фокус; возврат
не переводит фокус принудительно в другое поле и не требует показа клавиатуры.
Это относится и к возврату из экрана обновлений перед первым входом.

Данные существуют только в RAM живой формы. Пароль/TOTP не записываются в
Bundle, saved instance state, preferences, файлы, логи или backup. Не вводится
глобальный кэш credentials, чтение clipboard или новая autofill зависимость.
Process death и создание новой Activity могут очистить форму; восстановление
секретов в этих случаях не обещается.

Сохранение действует только пока эта форма остаётся текущим экраном. Нажатие
«Войти» отправляет точные значения по принятому API и сразу очищает пароль
и TOTP. Переход к ожиданию, явный auth reset, терминальный выход и обработка
ошибки с возвратом к новой форме явно заменяют старую форму; новая форма
пустая, как в исходной версии. Обычный foreground return не является таким
reset. Прежние foreground/generation/epoch fences отклоняют устаревшие
callbacks; возвращение в Activity само по себе не повторяет login.

На экране входа переход «Обновления приложения» расположен после полей и
кнопки «Войти», в нижней части формы с визуальным отступом от отправки.
Это компактный второстепенный элемент, а не большая кнопка над полями.
Надпись читаема, переход доступен с touch target не менее 48dp и обычным
accessibility focus. Явный клик открывает прежнюю `UpdatesActivity`.
Панель обновлений на authenticated экране сохраняет прежнее поведение.

## Публичный контракт и критерии приёмки

Activity: `ru.dewil.aicontrol.MainActivity`; lifecycle: `onCreate(Bundle)`,
`onStart()`, `onStop()`. Подсказки полей: «Логин», «Пароль», «Код TOTP»;
отправка: «Войти»; переход: «Обновления приложения».
Существующие внутренние reset seams для fault tests: `showLogin()`,
`showWait(String)`, `terminal()`, `login()`; они не становятся публичным API.
Независимые проверки используют синтетические данные, не реальные credentials.

- INV-AND-13 / INV-APP-06: первый stop/start сохраняет введённый логин;
  после вставки пароля второй stop/start сохраняет логин и пароль;
  вставленный TOTP также переживает следующий обычный цикл той же Activity.
  Проверяется точность всех значений и сохранение выбранного поля/selection
  в управляемом lifecycle test без внешнего владельца фокуса.
- INV-AND-13: начальный `onCreate` → `onStart` и повторные обычные циклы не
  заменяют уже видимые поля. Возврат из Updates оставляет форму пригодной
  для продолжения ввода. Отдельный реальный KeePass сценарий требует
  device acceptance; компиляция instrumentation не означает его исполнения.
- INV-APP-06: submission очищает пароль/TOTP; явная замена экрана/reset и
  возврат после ошибки создают пустую форму. Устаревший результат предыдущей
  отправки после stop/start не получает admission и не меняет новую форму.
- INV-AND-14: на login экране нет большой update кнопки над полями;
  единственный переход к обновлениям ниже «Войти», читаем, доступен и
  запускается явным кликом. Authenticated update bar не меняется.
- INV-APP-08: выпуск 0.1.3/code 4, package `ru.dewil.aicontrol`, прежний
  release certificate, min SDK 26/target SDK 36; build identity и signing
  проверяются независимо перед публикацией.

## Границы и принятые размены

Исправляется один корень: пересоздание видимой pre-login формы при обычном
возврате. Серверные API/config, grant lifetimes, provider auth, updater/vendor
реализация, хранение token и release канал не меняются. Исторический контракт
0.1.2/code 3 сохраняется в прежней feature spec; текущий выпуск для этого
исправления становится 0.1.3/code 4 с той же подписью.

Вопросов к пользователю нет. Следующий gate: независимые committed RED
по этому контракту, затем минимальная реализация и независимый SOURCE.
